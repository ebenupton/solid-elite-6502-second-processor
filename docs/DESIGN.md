# Filled Elite for the BBC Master — design spec (shared by all workers)

Base: the Elite Demonstration Disc source (ref/elite-demo-source-code-bbc-micro,
cassette Elite + self-playing autopilot), ported to the BBC Master 128 (65C02,
shadow RAM, sideways RAM banks 4-7). The demo's own logic is the stimulus: the
game logic must stay bit-for-bit identical to the original (same RNG calls, same
ship state per main-loop iteration), only rendering changes.

Target: same main-loop iteration rate as the original demo on a Model B
(~15-20 iterations/s in flight; measured with harness/run.mjs).

## Screen

Master-version geometry: custom MODE 1, 256 pixels wide, CRTC R1=64, R2=90,
R6=31, R12/R13=&0800 (screen starts &4000).

* Space view: 192 lines, y = 0..191, at &4000-&6FFF, 4 colours (2 bpp).
  Address of pixel row y, byte column c (c = x DIV 4, 0..63):
      &4000 + (y DIV 8) * &200 + (y MOD 8) + 8 * c
  MODE 1 pixel p (0 = leftmost of the byte, x MOD 4) of logical colour v (0..3):
      bit (7-p) = v bit 1, bit (3-p) = v bit 0
  so a byte of four pixels of colour 1 = &0F, colour 2 = &F0, colour 3 = &FF.
* Dashboard: 56 lines (7 char rows) at &7000-&7DFF, the same MODE 1 format and
  CMYK palette as the space view (256 x 56, 4 px per byte; screen line y =
  192..247), main RAM only. The whole screen is one MODE 1 screen: the loader
  sets the ULA (MODE 1, no cursor) and the palette once; the IRQ never changes
  mode or palette. The image is generated by tools/dashboard.py (build.sh runs
  it: build/DIALS1.bin, loaded to &7000, plus build/dashtab.asm, the colour /
  dot / bulb / missile tables INCLUDEd by the dashboard routines, and
  build/dashboard.png, build/dashmock.png previews). Layout (as Elite's): left
  labels x 2-14, bars x 16-47 (FS AS FU CT LT AL); scanner x 49-206, centre
  (126, line 28); compass ring centre (196, 11.5); right bars x 208-239 (SP,
  RL, DC, energy banks 1-4), labels x 241-254; bars on lines 2-4 of their row,
  scales on lines 6-7 (the bottom row: line 6 only, clear of the frame); missiles in row 6. Bars are one pixel per unit where the
  value allows (speed 0-40, temperatures/shields/altitude value / 8, fuel / 2,
  energy banks ENERGY / 2 at 32 per bank); roll/pitch are 2-pixel markers at
  0-30. The dashboard routines (DIALS, DIL, DIL2, DSEG, SCAN, ddot in main
  RAM; DOT, BULB, MSBAR, LCOL, HFCOL and the generated tables in bank 4)
  redraw only the bytes that change, and leave every game
  temporary, register and flag a caller can see exactly as the previous
  routines did (the game logic reads some: Y1 and the carry after SCAN).
* Split: the System VIA timer 1 interrupt is still restarted at each vsync (as
  the original: it is also the MOS's clock tick, which drives the sound), with
  a count (SPLITT) that puts its ACCCON write on the dashboard's first two
  lines (screen lines 192-193). It sets ACCCON D = 0 (the dashboard is in main
  RAM only) and GFRONT = 0 until the next vsync, because the frame layer's own
  ACCCON writes OR in GFRONT at any point of the frame (before, one landing in
  the dashboard showed shadow RAM there for the rest of the frame: the panel
  flicker). H_VSYNC keeps the real front buffer in GFRS and restores GFRONT.
  The loader copies the static dashboard image to shadow RAM &7000-&7DFF too,
  and nothing dynamic is drawn on the dashboard's first two lines (the scanner
  and compass dots are kept below them), so a split landing a line late is
  invisible. The MOS sometimes holds interrupts off for ~300 us (a split up to
  ~5 lines late), so the top row's bars (speed, forward shield) are written to
  both RAMs (DSEGD/DWR). Build option DASHDUAL = 1 (src/elite-source.asm) keeps
  the whole dashboard in both RAMs (every write goes to both via DWR), so
  nothing at all is done at the split; it is correct but ~1.3% slower, so it
  is off.
* Scanner: SCAN called from MV30 (the erase before a ship moves) is deferred
  until the next SCAN call that draws (normally the ship's redraw at the end of
  MVEIT), which then draws the erase and the redraw back to back, or neither
  if the dot hasn't moved, so ships never vanish from the scanner for a frame.
  EOR drawing commutes, and SCAN returns exactly as the original would have.
* Hyperspace: the original showed the rings in a mode 5 palette; here LOIN's
  direct-drawn line colour is settable (LCOL) and the hyperspace rings are
  drawn in yellow / magenta / cyan by ring size (HFCOL); launch rings stay cyan.
* Dashboard colours (all set in tools/dashboard.py): frame cyan; labels cyan /
  magenta; scales magenta; shields and energy yellow, speed / temperatures /
  altitude cyan, fuel yellow, danger red (magenta + yellow checker; green =
  cyan + yellow when flashing is on), roll / pitch markers yellow; scanner
  ellipse and grid magenta; scanner ships cyan (Python magenta, Thargoid and
  missile yellow, station green, asteroid red, cargo / pod blue = cyan +
  magenta); compass dot yellow (in front) or green (behind); missiles cyan
  (unarmed), yellow (armed), red (locked). The old split's escape-pod tint
  (dashboard colour 3 turned white) has no equivalent and is dropped.
* Double buffering: buffer A = main RAM &4000-&6FFF, buffer B = shadow RAM
  &4000-&6FFF (same addresses). ACCCON (&FE34) bit 2 (X) selects which one the
  CPU sees at &3000-&7FFF; bit 0 (D) selects which one is displayed. The IRQ
  sets D for the front buffer at vsync and clears D at the dashboard split (the
  dashboard is in main RAM; see Split above). Code/data touched while X=1 must live outside
  &3000-&7FFF (i.e. below &3000 or in sideways RAM &8000-&BFFF).

## Palette / colours: CMYK

Space view logical colours: 0 = blacK, 1 = Cyan, 2 = Magenta, 3 = Yellow.
Filled colours are 2x2 dithers of those four inks (tools/swatch35.py: 35 cells,
same phase conventions as Lander). A dithered colour is a PAIR of bytes:
(even-row byte, odd-row byte), each byte = 4 pixels, pixel x takes the ink at
(x AND 1, y AND 1) of the cell.

## Memory map (Master)

* &0000-&00E1 Elite zero page (as original). Renderer may use a ZP block that it
  saves/restores itself (see below); &E2-&EF unusable (MOS).
* &0100-&01FF XX3 vertex heap + stack (as original).
* &0300-&037F T% commander; &0400-&07F6 WORDS9; &0900-&0AAF K% ship slots;
  &0D40-&0F38 WP workspace (as original).
* &0F40-&3FFF Elite code (main RAM).
* &4000-&6FFF screen buffer A (main) / buffer B (shadow).
* &7000-&7DFF dashboard (main; MODE 1, tools/dashboard.py).
* &8000-&BFFF sideways RAM bank 4, permanently paged in: overflow Elite code,
  ship blueprints, renderer code and tables. (A second bank may be paged in for
  the duration of the render only, via a stub below &3000, if bank 4 overflows.)
* Bank 7, after the rasteriser's cold code (raster7.asm): Elite's cold code
  (src/cold7.asm: docked screens STATUS / market / equipment / charts / system
  data, the title screen and new-game set-up, DEATH, the commander template
  NA%), never run in the flight loop. Every entry keeps its name as a 5-byte stub
  where the code was (`.TT22 JSR far7 : EQUW TT22_7`); bank 7 code reaches
  everything outside bank 7 through `JSR far4 : EQUW target` stubs (src/far7.asm:
  A, X, Y and flags pass unchanged both ways, the caller's bank comes back, &F4
  follows ROMSEL). Bank 7 code reads no bank 4 data. Code used in flight, even
  rarely (hyperspace, launch, kills, the chart crosshairs), stays in main RAM or
  bank 4 (game-logic code can move between those two freely: bank 4 is always
  paged in while it runs).

## Frame model (space view)

The game loop runs unchanged, but drawing primitives no longer touch the
screen during the loop; they record into a display list:
  * ships: LL9 projects vertices (XX3) and face visibility (XX2) as before; the
    hook records each ship; each visible face is filled in a fixed colour (ships
    are not lit). tools/faces.py gives every ship two hue ramps and colours its
    faces so that faces sharing an edge never match (and mostly differ in hue),
    symmetric under the ship's mirror / rotation symmetries where the geometry
    allows; blueprint detail edges become filled polygons over their face
    (closed loops: engines, the docking slot), two-sided fin triangles (the
    missile: drawn before the body if neither face they stand between is
    visible, else after it) or lines (anything else);
  * sun / planet: per-row half-widths (the sun's LSO heap) or circle (planet
    K3,K4,K) -> the incremental "disc layer";
  * lines (lasers, planet meridians/craters), dots (explosion particles), stars;
  * text: a 32x24 text map (desired characters) rendered as an overlay.
    The map is also kept while drawing directly (QQ11 or GFORCE non-zero),
    and stars PIXEL draws directly are noted, so a screen that carries on in
    record mode without a TT66 (DEATH: "GAME OVER" and nWq's stardust are
    drawn at QQ11 = 6, then QQ11 = 0) starts with buffer 0's shown-text map
    right and its stray stars removed (src/frame_cold.asm).
At the end of each main-loop iteration FRAME renders the display list into the
back buffer and requests a flip at the next vsync.

Back-buffer render order (buffer b, two frames old):
 1. wait until the previous flip has happened;
 2. erase this buffer's old stars (they were only plotted on black pixels);
 3. per row: disc-layer diff — using this buffer's old disc span, old dirty
    extent and the new disc span, write disc colour where it is not already
    intact and black where something old is no longer covered;
 4. ships far-to-near (filled convex faces), lines, particles -> extend the new
    dirty extents (per row [min x, max x] in pixels);
 5. text overlay (cells whose content changed or whose pixels were overwritten),
    laser sights;
 6. stars, last (only on black pixels; positions remembered per buffer; as
    nothing is drawn after them, erasing them next time just restores black
    and needs no text redraw);
 7. flip request.
Clip window for fills: x 1..254, y 1..191 (the border box at x=0, x=255, y=0 is
never touched).
